\chapter{Implementation}
\label{sec:implementation}

The algorithms are implemented in Java. The original edition targeted Java~1.6 and the Eclipse IDE; the revised implementation builds with Maven on Java~8 or newer, which also runs the unit tests. This chapter describes the structure of the program, its performance engineering, the array-based B*-Tree, the defects found in the original implementation and the measures taken to make the results correct and reproducible.

\section{Architecture}

Fig.~\ref{fig:packages} shows the packages and the most important classes. The package {\tt module} contains the geometric primitives (a rectangle, a module with a name and an orientation, a placed module). The package {\tt btree} contains the immutable B*-Tree used by POEMS, the mutable array-based B*-Tree used by the fast evaluation and by LA-POEMS, and utilities for numbering the nodes, finding them, constructing the prototypes, placing the modules ({\tt Placer} with the contour {\tt PlacerCache}) and evaluating the placements. The package {\tt poems} contains the actions, the action sequences, the genetic algorithm ({\tt Population}, {\tt Individual}) and the POEMS iterations; {\tt poems.hybrid} contains LA-POEMS. The package {\tt program} contains the command line programs, the import of benchmarks, the export of results (SVG, DOT and GNUPlot files), the settings and the logging.

\section{The Original Design and its Cost}

The original implementation follows a functional style: trees, modules and action sequences are immutable, and every action builds a new tree, copying the unchanged parts. This makes the actions easy to reason about and to test, and the code is well structured and documented. Its performance, however, matters a lot: the algorithm evaluates millions of candidate floorplans, and the quality of the result within a given time grows with their number.

Profiling a run on n100 showed that most of the time was spent outside the algorithm itself (Table~\ref{tab:profile}). The contour was implemented as a sorted set of all placed modules walked from the top. Every search for a node by its number, every containment test and every evaluation built a stack and a linked list of the whole tree. And debug messages were formatted into strings, including complete action sequences, even though verbose mode was off and the strings were discarded.

\section{Speed-ups that Do Not Change the Results}

The following changes keep every computed value, including the sequence of random numbers, unchanged:
\begin{itemize}
\item the contour is a linked list of segments stored in arrays, and the placement passes the segment of the parent to its children, which makes the placement amortised linear (Section~\ref{sec:placement});
\item the fitness is computed from the bounding box only; the tree of placed modules is constructed only when it is needed (for the export of the final result);
\item finding a node, testing containment and evaluating a placement use recursion without allocating memory, while the iteration order of the trees is kept;
\item debug messages are formatted only in verbose mode.
\end{itemize}
For the same seed and the same number of iterations, the optimised program produces exactly the same results as the original one, which was checked on six benchmarks with two seeds each. Section~\ref{sec:rq1} reports the speed-ups.

\section{The Array B*-Tree}
\label{sec:arraybtree}

The immutable trees still allocate a new tree for every action. The class {\tt ArrayBTree} stores a B*-Tree in integer arrays: the left child, the right child, the parent and the module of every node, the node of every module, and the orientation of every module. The actions modify the arrays in place:
\begin{itemize}
\item flip, mirror and rotate visit the affected subtree;
\item exchange value swaps two modules in $O(1)$;
\item exchange node and hang node check the ancestor relation by walking up to the root, and relink the nodes in $O(1)$;
\item move node removes and inserts a node in $O(1)$, plus the walk to the top of the rightmost branch of the left child.
\end{itemize}
The placement is an iterative depth-first traversal with an explicit stack and the array contour, and it supports the early termination of Section~\ref{sec:earlyexit}. A copy of the tree is a copy of six arrays. Two trees are compared by a simultaneous depth-first traversal comparing the modules, their orientations and the presence of children, so the comparison does not depend on how the nodes are numbered internally.

The array actions must behave exactly like the original immutable actions. A unit test applies 10\,000 random actions of all seven types, with random parameters, to both representations of random instances. After every action, it checks that the trees are equal and that the placed areas agree. A second test applies 10\,000 random action sequences to random prototypes and checks that the fitness computed on the array representation, including the identity check, equals the fitness computed on the immutable trees. Complete runs of POEMS with both evaluations give identical results for the same seed and number of iterations.

\section{Defects Found and Fixed}
\label{sec:defects}

Table~\ref{tab:defects} lists the defects found in the original implementation. The first four changed the behaviour of the algorithm described in the original edition, the fifth made the program hang for $N = 1$, and the last two did not influence the search. The identity check had the largest effect: it made pure rotations impossible, although rotation is one of the most useful moves (Section~\ref{sec:rq3}). In addition, twelve unit tests failed on Java~9 and newer because of a type cast in a test utility, and one test expected a prototype that the code never produced; the test suite now passes completely (80 tests).

\section{Correctness and Reproducibility}

Besides the unit tests, every result reported in Chapter~\ref{sec:testing} was checked by an independent validator. It checks that every module of the instance appears exactly once, with its original or rotated dimensions, at non-negative coordinates, and that no two modules overlap. All runs passed. The random number generator can be seeded, so a run with a given seed and a given number of iterations or evaluations is reproducible; runs with a time limit are reproducible up to the number of steps made within the limit. A benchmark runner ({\tt program.Benchmark}) solves one instance with a given seed, time limit and parameters, validates the result and prints a line of comma-separated values. It can also write the time and quality of every improvement of the best solution (the convergence trace) and the coordinates of the modules of the final floorplan. The scripts used for the experiments are described in Appendix~\ref{sec:usage}.
